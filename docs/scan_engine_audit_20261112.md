# 🔬 7단계 스캔 엔진 정밀 감사 — 구조·결함·시점별 검증 (2026-11-12)

작업 브랜치 `feat/weekly-index-forecast`, 기준일 2026-11-12 KST. 요청 범위: **화면(첨부 스크린샷의 출력 표·머리말)은 건드리지 않고** 엔진 내부를 분석·수정한다.
검증 도구는 `scripts/audit_scan_ranking.py`, 결과는 `docs/backtests/scan_ranking_audit_20261112.json`, 회귀 테스트는 `tests/test_scan_pipeline_audit_20261112.py`·`tests/test_scan_audit_harness_20261112.py`.

## ① 요약

[사실] 7단계 점수 체계(BQS·FWS·NCS)는 날짜별 교차단면에서 **미래 5·10·20거래일 초과수익률의 순서를 약하게만 맞춘다**(순위상관 IC +0.012~+0.028, 삼중 장벽 승패 AUC 0.5055, 95% 구간 0.495~0.515가 0.5를 포함). 거래량 세 항목(BQS 거래량 보너스·FWS 거래량 위험·BIS)은 어느 지평에서도 예측력이 없었고, 새로 시험한 거래량 특징 9종(RVOL·OBV·CMF·MFI·거래대금·상하락 거래량비 등)과 LightGBM 순위 모델도 **채택 기준을 통과하지 못했다**. 그래서 점수 수식과 화면 값(돌파 점수=BQS)은 바꾸지 않았고, 성능이 개선됐다고 주장하지 않는다. 다만 BQS는 확률이 아닌 점수여서, 표 머리글 이름만 사용자 승인으로 "돌파 신뢰도"에서 **"돌파 점수"**로 바꿨다(툴팁은 이미 "BQS 점수"라 그대로, 셀 값·열 순서·개수 불변).

[사실] 대신 엔진이 **조용히 틀린 결과를 내던 경로**를 고쳤다: 미국 종목이 한국 규칙으로 평가되던 시장 오표기, 종목 하나의 NaN이 시장 전체 스캔을 중단시키던 구조, 낡은 시세(거래정지·누락)의 혼입, 진행 중 막대가 기법 게이트에 섞이던 문제, 품질 등급이 순위에 세 번 반영되던 중복, 재무정보가 소수 종목에만 도착해 순위가 우연으로 갈리던 비결정성, 허스트를 스냅샷마다 두 번 계산하던 낭비(스냅샷 비용 −37%).
고친 모든 항목은 수식이 같은 구간에서 **직접 비교로 동일성을 확인**했다: 새 코드로 다시 만든 68,210개 시점 행이 변경 전 행과 71개 수치 열·모든 문자 열에서 비트 단위로 같다(`BQS/FWS/NCS/상태/목표값` 포함). 전체 테스트는 961개(+하위 검사 6개) 통과 — 변경 전 기준 934개에 27개를 추가했다(아래 ⑦). RS 꼬리 정렬(결함 5)은 종목 창과 벤치마크 창 길이가 다를 때만 값이 달라지는데, 라이브 표본(미국 30·한국 30종목)은 전부 길이가 같아(미국 SPY 251봉, 한국 ^KS11 245봉) 현재 화면의 돌파 점수 값은 그대로다.

[사실] 첨부 화면의 "필터 통과 0 / 진입 준비 0 / 관찰 대기 0"은 버그가 아니라 **기법 검증 규칙**의 결과다(`models/technique_prune.json`: `hybrid_breakout`이 한국 `INSUFFICIENT`, 미국 `DROP`, `strict_validated_only=true`라 모든 후보가 차단). 이 정책은 유지하고, 원래 2단계 통과 수와 단계별 잔존 수를 응답의 추가 필드(`stage_funnel`·`stage2_passed`·`entry_signal`)로 노출했다. 화면이 읽는 필드는 하나도 바꾸지 않았다.

## ② 실제 구조 — 7단계와 그 위에 얹힌 선정 계층

`market_briefing/scan_engine.py::run_full_scan`이 7단계를 종목마다 순서대로 적용하고, `api/index.py`의 `/api/scan`이 그 앞(수집)과 뒤(박스 플랜·선정)를 맡는다. 단계는 **누적 순차 필터가 아니라 "플래그를 쌓고 점수를 따로 계산하는" 구조**다: 탈락시키는 것은 1단계(QMJ)뿐이고 나머지는 상태·플래그·점수를 붙인다.

| 단계 | 담당(파일·함수) | 입력 → 출력 | 핵심 규칙 |
|---|---|---|---|
| 0 수집 | `api/index.py` 스캔 라우트 | 유니버스(한국 46·미국 122) → 일봉 250봉·벤치마크·info | `yf.download` 1회(벌크) → 종목별 스냅샷 → info 6워커. 시간 예산 42초. 미국 $23 초과 제외(`is_scan_price_eligible`) |
| 1 Universe·QMJ | `quality_filter.score_quality` | info(ROE·부채비율·매출성장) → 등급 high/medium/low/junk/unknown | low·junk는 **탈락**, unknown은 통과(배율 0.5). 일부 지표가 없으면 +0.5점씩 |
| 2 기술 필터 | `run_technical_filters` | 스냅샷 → 6개 불리언 | 가격>MA200, ADX≥20, +DI>−DI, ATR%<8(고위험 12), 효율≥30, 데이터 유효. **모두 참**이어야 통과. 허스트<0.5는 경고만 |
| 3 분류 | `classify_candidate` | 가격·진입 트리거 → READY/WATCH/FAR | 거리≤2%(이미 돌파 포함) READY, ≤3% WATCH, 그 외 FAR. ATR 급증(`≥1.3×과거 ATR`) 시 READY→WATCH |
| 4 점수·랭킹 | `dual_score_v2.compute_bqs/fws/ncs` | 스냅샷 → BQS·FWS·NCS, `rank_candidate` | `NCS = clamp(BQS − 0.8·FWS + 10) − 패널티`. BQS 10항목(ADX·DI·ATR%·20일 고점 근접·레짐·RS·거래량·주간 ADX·BIS·허스트) |
| 5 리스크 게이트 | `validate_risk_gates` | 사이징 → 통과/탈락 | 포지션·섹터·총위험 한도. **포트폴리오 입력이 없어 구조적으로 항상 통과** |
| 6 추격 방지 | `check_anti_chase`·`check_pullback_continuation` | 가격·트리거·ATR → 통과/WAIT_PULLBACK/풀백 재진입 | 초과 ATR>0.8 또는 갭>4%면 WAIT_PULLBACK. **2단계 통과 종목에만** 평가 |
| 7 최종 구성 | `ScanCandidate`·정렬 | 위 결과 → 후보 목록 | 정렬은 API가 종합점수로 다시 하므로 사실상 장식 |
| 선정 | `api/index.py` | 후보 → 15개 | ① 보조 신호(리더·모멘텀·VCP) 승격 ② 종합점수 = 0.35·상태 + 0.40·NCS + 0.25·품질 ③ **박스 실행 플랜이 완성되고 현재가<1차<2차<3차 목표인 종목만** ④ 등급(1:진입권, 2:FAR, 3:필터 미통과) 순 채움 + 시총·섹터 분산(MMR) |

두 가지 구조적 사실이 결과를 좌우한다.
1. **기법 검증 게이트**: 3단계 직후 `technique_allowed("hybrid_breakout", 시장, 조건)`이 모든 후보를 차단해 `passes_tech_filters=False`·READY→WATCH가 된다. 그래서 선정은 항상 3등급("관찰 후보 보강")이고, 순서는 종합점수가 정한다. 보조 신호 승격(리더·모멘텀·VCP)도 같은 이유로 막힌다.
2. 박스 플랜 완성 여부는 **순위가 아니라 거르기**에만 쓰인다. 완성 종목은 "박스 중간 아래"에 있어서, 상태 축(20일 고점 근접)이 높은 종목과 구조적으로 겹치기 어렵다(라이브: 선정 14~15개 중 거의 모두 FAR).

### 확인했으나 바꾸지 않은 것

| 항목 | 이유 |
|---|---|
| 기법 검증 게이트의 정책 | 검증되지 않은 기법의 "진입 준비" 표시를 막는 의도된 안전장치. 바꾸려면 규칙 파일 재검증이 먼저다 |
| 5단계 리스크 게이트 | 계좌 입력이 없어 항상 통과 — 삭제 대신 사실만 기록 |
| 주간 ADX(BQS 항목) 항상 0, `is_monday` 미연결, `dual_aligned`=False·`regime_stable`=True 고정, `days_to_earnings` 미공급(실적 블록·패널티 비활성) | 활성화하려면 새 데이터·새 조건이고, 실적 일정은 시점별 이력이 없어 검증할 수 없다. 후속 과제 |
| 7단계 정렬(`_sort_key`) | API가 종합점수로 다시 정렬하므로 영향 없음 |
| `quality_filter`의 `round()`(은행가 반올림) | 점수 2.5→2(medium), 1.5→2, 0.5→0. 우연히 보수적(정보가 일부 빠진 종목이 high가 되지 않음)이라 동작을 고정만 하고 두었다 |

## ④ 시점별(walk-forward) 검증 (D)

## ⑥ 남은 한계와 후속 과제 (F)

1. **[높음] 점수의 예측력이 약하다.** AUC≈0.505. 박스 플랜·확률의 별도 감사(2026-11-05·11-11)와 같은 결론이다. 순위가 선정 품질을 높인다는 근거는 없고, 선정은 "박스 플랜 완성" 거르기에 크게 좌우된다. 박스 플랜 완성 여부 자체의 시점별 성과는 이 도구에 포함하지 않았다(종목·시점마다 플랜 엔진 필요).
2. **[완료] 스캔 표 머리글 "돌파 신뢰도" → "돌파 점수".** BQS는 확률이 아니며 승패를 구분하지 못한다(AUC 0.5055). 사용자 승인(2026-11-12)으로 머리글 이름만 바꿨다 — `api/index.py` 머리글 한 줄과 이를 고정하던 테스트(`tests/test_scan_engine_rendering.py`·`tests/test_vcp_scan.py`)만 달라졌다. 감사 전 스냅샷과 비교하면 HTML/JS 영역에서 바뀐 것은 머리글 한 줄과 그 이름을 적은 주석 한 줄뿐이다. 종목 상세 탭의 같은 이름("돌파 신뢰도", BIS 0~15점)은 다른 지표라 남아 있으니, 혼동이 되면 그 이름도 정리한다. 이전 문서(`box_execution_plan_20261105.md`, `tdd_scan_output_20260923.md`)의 "돌파 신뢰도"는 당시 이름이다.
3. **[중간] 거래량 세 항목 제거**는 확정 근거가 없어(각 |t|<2) 전향(forward) 표본이 쌓인 뒤 재검증한다: `python scripts/audit_scan_ranking.py --reuse`.
4. **[해결 — ⑧] 정보 수신 예산.** 원인은 예산 배분이 아니라 앱이 yfinance 의 영속 쿠키 캐시를 꺼서 **모든 HTTP 요청이 쿠키를 다시 받고 그 요청이 전역 락 안에서 직렬로 일어난 것**이었다. 쿠키 재사용(`market_briefing/yf_cookie.py`, 복원 `STOCKORACLE_YF_COOKIE_REUSE=0`)을 켜자 이 PC의 미국 표준 스캔(`/api/scan?market=US&refresh=1`)이 60.9초 → 23.4초(반복 22.4·23.0·22.6초), `data_quality.quality_coverage` 0.065 → **1.0**, `quality_stage` `skipped_low_coverage` → `applied`가 됐다(한국 42.6초 → 13.2초). 후보 (a) 일 단위 info 캐시·(b) 일봉 증분 수집·(c) 종목별 `Ticker.history` 풀은 측정상 기각(시간 이득 없음 또는 콜드 스캔 미해결, 표는 ⑧). **미측정**: Vercel 실제 환경. **부수 효과**: 미국 QMJ 단계가 처음으로 실제 적용돼 93종목 중 42종목(45%)이 1단계에서 탈락한다(한국은 46종목 중 7종목, 15%).
5. **[중간] 실적 일정(days_to_earnings) 미공급**으로 실적 블록·패널티가 꺼져 있다. 시점별 일정 없이는 검증할 수 없다.
6. **편향**: 유니버스가 2026-11 유동성 기준(생존·선정 편향), 일봉 기반(장중 체결·호가 미반영), 단일 5년 사이클, 겹치는 지평의 표본 의존(뉴이-웨스트로 보정했으나 완전하지 않음), 후보를 여럿 본 탐색 편향.

### 6) 부수 효과와 남은 한계

1. **미국 QMJ 단계가 처음으로 실제 적용된다.** 93종목 중 42종목(low 28·junk 14, 45%)이 1단계에서 탈락한다(한국 46종목 중 7종목, 15%). 라이브 선정 15개 중 11개가 이전 목록과 같고, 빠진 4종목(VFC·PENN·RIG·OPEN)은 모두 `low`, 들어온 4종목(UPST·GAP·HBAN·AAL)은 모두 `medium`이다. 이는 감사 전 설계 그대로이지만 미국 선정이 눈에 띄게 달라지는 변화이므로 알려 둔다. **사용자 확인(2026-11-13): 그대로 둔다 — 미국 QMJ 적용 유지.** 되돌리기(필요해질 때): 이전 동작(느린 수집 → 수신률 4%대 → 단계 꺼짐)은 `STOCKORACLE_YF_COOKIE_REUSE=0`으로 재현되고, 수집은 빠르게 두고 QMJ 단계만 끄려면 `STOCKORACLE_SCAN_QUALITY_MIN_COVERAGE=2`(수신률은 1을 넘지 못해 항상 끔)로 설정한다.
2. **Vercel 미측정.** 절대 시간은 서버 환경의 지연에 좌우된다. 구조(요청의 절반이 쿠키 요청, 락 직렬)는 같으므로 이득은 있을 것이나 수치를 단정하지 않는다. 운영에서는 `data_quality.timings_s`·`quality_stage`·`yf_cookie_reuse`로 확인한다.
3. **야후로 가는 동시 요청이 늘어난다.** 락이 풀려 `download`가 실제 병렬이 된다(스레드 수 = 논리 CPU × 2, 이 PC는 24). 쿠키 재사용을 켠 상태의 미국 스캔 4회·한국 스캔 3회·`Ticker.history` 풀 3종·`download`·`info` 93종목 동안 수집·조회 누락이 없었지만(수집 종목 수와 수신률이 매번 정상) 레이트리밋은 환경 의존이다. 문제가 생기면 `STOCKORACLE_YF_COOKIE_REUSE=0`으로 즉시 복원한다.
4. `YfData._cookie`·`_get_cookie_basic`은 yfinance 의 비공개 구조다. 버전이 바뀌어 맞지 않으면 감싸기가 `False`를 돌려주고(예외 없음) 이전 동작이 남으며, 진짜 `YfData`를 가짜 세션 위에서 돌리는 테스트(1)~(4)가 먼저 깨져 알려 준다. **버전 가드(2026-11-13 추가)**: `requirements.txt`가 `yfinance>=0.2.36`이라 설치 버전이 달라질 수 있어 소스를 열어 확인했다 — PyPI 최신 1.8.0은 같은 `(self, timeout=30)` 모양과 같은 쿠키 재요청 구조(그래서 수정이 계속 의미가 있다)이지만, 0.2.54는 `_get_cookie_basic(self, proxy=None, timeout=30)`이고 `_cookie`가 실제 쿠키 값이다. 처음 구현은 시그니처가 `(self, timeout=30)`로 고정돼 있어 구버전에서 모든 yfinance 요청이 `TypeError`로 깰 수 있었으므로, 이제 검증한 모양일 때만 감싸고(다른 모양이면 `False` = 이전 동작) 인자는 그대로 통과시킨다. 검증은 두 버전의 소스 열람과 스텁 테스트이며 **1.8.0을 실제로 실행해 속도를 재지는 않았다**.
5. 이 수정 전부터 있던 별개 한계는 그대로다: 점수 예측력(⑥-1), 실적 일정 미공급(⑥-5).
