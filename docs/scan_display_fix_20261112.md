## ③ 분석

**PR: 사용자 가치와 수정 범위 재정의.** 첫 번째 검토 기준으로 선택한 이유는 사용자가 이미 기능 확대를 철회하고 원래 화면의 복구를 요청했기 때문이다. 화면에 표시되는 기간·자본·보유 수량 입력은 이번 목표에 포함되지 않는다. 정상 기준은 수정 이전의 시장 선택과 스캔 모드 선택, 그리고 목표가·손절 기준·재진입 후보·예상 기간·도달 확률 표다. 로컬 HTML은 이 기준을 만족한다. 따라서 추가 패널의 레이아웃을 다듬거나 삭제된 함수의 임시 구현을 만드는 접근은 사용자 목표를 충족하지 못한다. 이 판단은 복구 이력과 첨부 화면을 근거로 하며, 사용자가 별도로 요청하지 않은 주문 실행이나 보유 종목 진단을 요구사항으로 추정하지 않는다.

**MDA: 파일·실행 위치·시간 차원 비교.** 두 번째로 선택한 이유는 같은 프로젝트라도 로컬 소스, 원격 저장소, 운영 HTML의 내용이 서로 다를 수 있기 때문이다. 비교 결과 원격 API의 정규화 SHA-256은 `84e7715320712dc00232d918712cdc4e2b99c0a6a5d902c1113a712188428a51`로, 보관된 원복 전 API와 일치했다. 원격 엔진의 SHA-256은 `269acfc0c815b9cd56f81a67f92440eaa86fa86f657551603abc0dfe6c41288a`로, 원복된 로컬 엔진과 일치했다. 박스 예측·시퀀스·플랜·스캔 플랜·거래량·완료봉 모듈, 패키지 초기화 파일과 Vercel 설정도 원격과 로컬의 파일 바이트가 같았다. 조사한 파일 중 API만 이전 내용이었다. 이 비교는 전체 원격 저장소가 정상이라는 뜻이 아니라 장애와 직접 관련된 파일 집합의 상태를 뜻한다. 원격 조회 이후의 변경까지 보장하지 않는다.

**CS: 원인과 해결 효과를 구조화.** 세 번째로 선택한 이유는 가장 작은 수정으로 import 실패와 잘못된 화면을 동시에 해결해야 하기 때문이다. Python은 `from ... import`에 없는 이름이 하나라도 있으면 해당 문장에서 실패한다. 첨부 오류의 import 문장을 원격 소스에서 AST로 추출해 실행하자 같은 `ImportError`가 재현됐다. 실제 계산을 실행하거나 외부 주가 공급자를 호출하기 전의 실패다. 원격 API에는 후속 삭제 함수와 모듈 참조도 있으므로 첫 이름에 대해서만 예외 처리하면 다음 참조에서 다시 실패하거나 화면만 이전 상태로 남을 수 있다. 원래 API 파일을 정상 엔진과 함께 사용하는 것이 원인에 직접 대응한다. 이 결론은 소스 비교와 재현을 근거로 하며, 배포 로그를 열람해 확인한 것은 아니다.

**반증과 위험 재평가.** 브라우저 캐시만의 문제라는 가설도 확인했다. 캐시를 우회한 운영 HTML 응답은 `X-Vercel-Cache: MISS`, `Age: 0`이었는데도 이전 입력란을 포함했다. 따라서 브라우저 새로고침만으로 해결된다는 결론은 반증된다. 기존 HTML의 1시간 CDN 캐시와 스캔 응답의 stale 허용은 별도의 재사용 경로이므로 보조 수정으로 해제한다. Vercel 문서도 배포 시 캐시 무효화를 설명하므로, 캐시 설정 자체를 파일 불일치의 원인으로 단정하지 않는다. 이미 열린 탭의 DOM은 새 코드 배포만으로 바뀌지 않으며, 배포 후 페이지를 다시 열어야 한다.

**일곱 관점의 교차 점검 결과.** 분야 전문가는 박스 가격 계산 유지, 회의론자는 캐시 단독 가설 반증, 대안 검토자는 정상 API 전체 교체, 반대 검토자는 호환용 빈 함수의 불충분함을 확인했다. 위험 검토자는 파일 일부만 교체하는 경로와 서버 내부 캐시의 구분을 점검했고, 사실 검증은 해시·실제 import·브라우저 DOM·테스트 결과를 대조했다. 최종 판단은 로컬 수정과 운영 반영을 구분해서 보고하는 것이다. 이는 검토 관점의 요약이며 별도의 심사자 일곱 명이 독립 실행했다는 주장은 아니다. 실시간 스캔 한 번의 성공은 예측 정확도나 수익성을 입증하지 않는다.

## ④ 아이디어와 적용 항목

1. **정상 API 파일 전체를 교체 단위로 사용한다 — 준비 완료.** 이번 장애에는 하나의 import 이름 외에도 철회된 화면과 모듈 참조가 함께 포함돼 있다. 그래서 오류에 나온 줄만 지우는 방법보다 로컬에서 복구·검증한 `api/index.py` 전체를 교체하는 편이 요구사항과 맞는다. 해당 파일의 기존 사용자 작업은 Git HEAD로 초기화하지 않고 보존했다. 비교한 나머지 스캔·박스 모듈은 이미 원격과 같으므로 신규 계산 체계를 추가할 이유가 없다. 파일 교체 후에는 실제 배포가 같은 API를 사용하는지 확인해야 한다. 로컬 수정만으로 운영 URL의 코드가 자동 변경된다고 안내하지 않는다.

2. **삭제된 함수의 빈 구현을 추가하지 않는다 — 적용.** `finalize_scan_safety`라는 이름만 다시 내보내면 현재 오류 문구는 사라질 수 있다. 그러나 호출자가 기대하는 인자·반환값·후처리를 보장하지 못하고 `finalize_box_execution`, `scan_execution` 참조가 다음 오류가 될 수 있다. 특히 이전 UI가 그대로 남아 사용자가 원복 실패로 인식하는 문제가 계속된다. 이번 복구에서는 실제로 존재하는 원래 스캔 인터페이스만 사용한다. 앞으로 인터페이스를 변경할 때도 함수 이름의 존재만 확인하기보다 호출 지점과 화면의 계약을 함께 검증하는 것이 적절하다. 이름만 맞춘 성공 응답은 복구의 증거로 취급하지 않는다.

3. **원래 화면의 입력 구조를 검사한다 — 테스트 적용.** 스캔 페이지 범위를 추출해 select 요소가 `scan-market`, `scan-mode` 두 개인지 검사한다. 철회된 기간·자본·종목·보유 점검 요소가 없는지도 확인한다. 기존 렌더링 테스트는 12열의 순서, 제거한 과거 열의 부재, 빈 결과 행의 열 개수까지 검증한다. 문구 하나를 수정할 때마다 화면 전체가 흔들리지 않도록 외형의 핵심 계약을 확인하는 방식이다. 실제 브라우저에서도 동일한 선택란과 열 목록을 확인했다. 이 검사는 모든 CSS 픽셀의 동일함을 주장하는 것이 아니라 사용자가 이용하는 입력과 결과 구조의 복구를 보장하기 위한 기준이다.

4. **거래량 개선과 화면 복구를 독립적으로 보존한다 — 적용.** `box_volume.py`와 이를 사용하는 박스 시퀀스·플랜·스캔 요약 모듈을 이번 장애 해결 과정에서 다시 수정하지 않는다. 완료봉 거래량 확인, 약한 돌파의 조건부 전환, 원래 목표 가격의 유지라는 이전 보완 범위를 그대로 둔다. 원격 비교에서도 관련 모듈은 로컬과 같았다. 화면 오류가 있었다는 이유로 이 모듈까지 일괄 되돌리면 사용자가 실제로 원했던 거래량 개선을 잃을 수 있다. 따라서 복구의 완료 기준에는 import와 표 출력뿐 아니라 거래량 회귀 테스트의 통과도 포함한다. 이는 거래량이 매도 체결을 보장한다는 의미가 아니다.

5. **HTML의 HTTP 저장을 금지한다 — 수정 완료.** HTML에 스캔 JavaScript가 함께 들어 있으므로 오래된 HTML을 재사용하면 이전 화면과 요청 방식도 함께 남는다. `/`, `/index.html` 응답을 `Cache-Control: no-store`로 바꿨다. 배포한 현재 코드를 새로 요청하도록 하는 목적이며, 열린 페이지의 DOM을 강제로 교체하는 기능은 추가하지 않았다. 이 변경으로 페이지 요청이 서버에 도달하는 빈도는 늘 수 있지만 외부 시세 수집을 매번 새로 수행하도록 바꾼 것은 아니다. 이번 파일 혼재의 근본 해결은 여전히 정상 API 교체이며, 캐시 해제는 이후 화면 재사용 경로를 줄이는 보완 조치다.

6. **스캔 응답과 오류를 CDN에 남기지 않는다 — 수정 완료.** 기존 예외 경로는 HTTP 200에 `error` 필드를 담아 반환하므로 상태 코드만 보고 캐시 허용 여부를 결정하면 import 오류도 잠시 저장될 수 있다. `/api/scan`의 응답은 성공·오류를 모두 `no-store`로 처리한다. 새로고침 요청 뒤에 stale 응답이 표시되는 경우도 방지한다. 서버 내부의 5분 스캔 결과 캐시는 유지하므로 외부 수집량을 불필요하게 늘리지 않는다. 브라우저·CDN 캐시와 Python 내부 계산 캐시는 역할이 다르며, 이번 수정은 오류 화면을 고착시킬 수 있는 HTTP 재사용 경로에 한정한다. 다른 API의 캐시 전략은 이번 범위에서 확대 변경하지 않는다.

7. **브라우저 요청도 최신 응답을 요구한다 — 수정 완료.** `runScan`의 fetch에 `{cache: 'no-store'}`를 지정했다. 요청 URL과 응답 형식, 시장·모드 선택 방식은 그대로 둔다. 일반 실행과 새로고침 버튼의 `refresh=1` 구분도 보존한다. 서버 응답 헤더만 바꾸는 것과 함께 브라우저의 재사용을 명시적으로 제어하기 위한 변경이다. 실제 테스트에서는 서버가 돌려준 결과를 기존 `renderScanResult`가 받아 표시했고, 오류 영역은 숨겨지고 실행 버튼은 다시 활성화됐다. 별도의 데이터 어댑터나 가짜 성공 응답을 넣지 않았기 때문에 이전 화면 복구와 계산 결과 검증이 같은 실행 흐름에서 이뤄진다.

8. **실제 import 문장을 회귀 테스트로 실행한다 — 테스트 적용.** API 소스를 AST로 읽어 스캔 엔진·박스 플랜·철회된 실행 모듈 관련 import 문장을 추출하고, 그 문장만 실행한다. 주가를 수집하지 않아도 삭제된 심벌과 누락 모듈을 탐지할 수 있다. 테스트에 별도의 함수 목록을 복제하면 API에 새로 추가된 잘못된 이름을 놓칠 수 있으므로 실제 소스의 import를 검사한다. 확보한 원격 API의 import에는 첨부와 같은 오류가 재현됐고 로컬의 문장들은 통과했다. 선택적 외부 서비스의 모든 호출을 검증하는 검사는 아니며, 이번 장애가 발생한 파이썬 연결 계약에 초점을 둔다.

9. **교체 파일과 해시를 한 묶음으로 제공한다 — 준비.** 수정 API와 현재 스캔·박스 모듈을 경로를 유지한 ZIP에 담고 SHA-256 목록으로 동일성을 확인한다. 이 묶음은 기존 프로젝트에 덮어쓸 소스 업데이트이며 의존성과 모델을 포함한 독립 실행 배포본이라고 부르지 않는다. 철회된 실험 파일, 데이터셋, 환경변수, 복구용 백업은 포함하지 않는다. 사용자가 일부 파일만 올려 다른 시점의 API를 남기는 실수를 줄이는 목적이다. 묶음 생성 뒤에도 포함 바이트가 현재 검증한 파일과 같은지 재확인한다. 운영 저장소 업로드와 Vercel 배포는 파일 작성과 구분해서 명시하며 자동 완료를 주장하지 않는다.

10. **계산·응답·화면을 단계별로 검증한다 — 적용.** import와 화면 구조 검사만 통과해도 외부 시세 수집 이후의 결과 출력이 실패할 수 있으므로 실제 로컬 스캔과 브라우저 렌더링을 추가 확인한다. 미국 핵심 종목 스캔은 33종목을 검토해 3후보를 반환했고 각 후보가 12셀로 표시됐다. 전체 테스트도 934개와 하위 검사 6개가 통과했다. 빈 결과, 수집 시간 예산, 데이터 공급자 제한은 정상 계산에서도 발생할 수 있으므로 모든 실행이 반드시 후보를 낸다고 가정하지 않는다. 화면 정상화와 예측 정확도 향상은 서로 다른 평가 대상이며, 이번 성공 기록을 미래 가격 예측 성능의 증거로 사용하지 않는다.
